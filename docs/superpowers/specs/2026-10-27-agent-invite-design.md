## 1. 目的と背景

いまの先行版は、求職者が全員共通の招待コードで入り、職種・経歴・応募先を自分で入力し、記録は自分のブラウザにだけ残る。

依頼者の運用では、**エージェント(キャリアアドバイザー)が先に求職者と応募先の情報を入れ、その求職者・応募先専用のリンクを送る**。求職者はリンクを開くだけで、マイクの確認からすぐに面接を始められるようにしたい。結果は求職者とエージェントの両方が見られるようにする。

これにより、

- 求職者は入力や案内を飛ばして、本番に近い練習にすぐ入れる。
- エージェントは、応募先に合わせた練習を用意し、何回練習したか・どこが弱いかを見て面談に活かせる(要件 US-07、US-08)。
- 共通の招待コードがなくなり、リンクごとに止められるので、広まって誰でも使える状態を防げる。

## 2. 依頼者が決めたこと

| No. | 決定 |
|---|---|
| U-1 | ログインして使うのはエージェント。求職者はログインしない |
| U-2 | エージェントが求職者の情報と、応募する企業の情報を入れて、招待リンクを作る |
| U-3 | 求職者がリンクを開いたら、マイクの確認の画面から始まり、すぐ面接を始められる |
| U-4 | 結果は、エージェントと求職者の両方が見られる |
| U-5 | エージェントの画面は、求職者ごとに整理する(同じ求職者が複数の企業を受けるため) |
| U-6 | リンクは「求職者 × 応募先」ごとに1つ。同じリンクで何回でも面接を受けられる。違う応募先を入れたら、別のリンクになる |
| U-7 | 画面の見本(エージェント①担当の求職者、②求職者の詳細、③応募先を追加してリンクを作る、④結果。求職者⑤リンクを開いた最初の画面、⑥面接が終わったあと)のとおりでよい |

## 3. 目標・対象外・やってはいけないこと

**目標**

- エージェントがログインし、求職者と応募先を登録して、リンクをコピーできる。
- 求職者がリンクを開き、音と声の確認 → 面接 → 結果まで、入力なしで進める。
- 同じリンクで何回でも練習でき、求職者はそのリンクでの過去の結果を見返せる。
- エージェントは、求職者ごと・応募先ごとに、練習の回数・点数・結果・会話の記録を見られる。

**対象外(今回は作らない)**

- 求職者のログイン、求職者が自分で応募先や経歴を入れる機能。
- 練習課題の期限、コメント、スコアのグラフ、管理画面(要件 F-10-3〜5、F-12 の画面)。
- エージェントが結果を見たことの記録(要件 8.4 の操作ログ)。本番で多くのエージェントが使う前に加える。
- エージェントを画面から招待する機能(当面は管理者が Supabase の画面で追加する。7章)。
- いまの先行版(共通の招待コードの `/join`、ブラウザ保存)の削除。今回は残し、新しい流れが動いてから扱いを決める。

**やってはいけないこと**

- 求職者の画面に、内部の区分・点数の判定基準・エージェント向けの言葉を出す(求職者向けの表示は前向きに)。
- 結果がエージェントに共有されることを、求職者に知らせないまま練習させる。
- リンクの文字列から、ほかの求職者のリンクを推測できる。
- 求職者が、リンクを書き換えて面接の設定や応募先の情報を変えられる。
- エージェントが、ほかのエージェントの求職者を見られる。

## 4. 画面と流れ

### 4.1 エージェント

| 画面 | URL(案) | 内容 |
|---|---|---|
| ログイン | `/agent/login` | メールアドレスを入れると、ログインのリンクと6桁の確認コードが届く。リンクを押すか、コードを入れてログインする。一度ログインした端末では、ログインしたまま |
| ① 担当の求職者 | `/agent` | 自分の求職者の一覧。名前・職種・応募先の数・最新の点数と日付。「+ 求職者を追加」 |
| 求職者の追加・編集 | `/agent/seekers/new`、`/agent/seekers/[id]/edit` | 名前、職種、経歴、転職理由 |
| ② 求職者の詳細 | `/agent/seekers/[id]` | 求職者の情報(直す)と、応募先ごとの招待リンク(応募先・職種・選考段階・面接官の雰囲気・時間、練習の回数・最新の点数、「リンクをコピー」「結果を見る」)。「+ 応募先を追加してリンクを作る」 |
| ③ 応募先の追加・編集 | `/agent/seekers/[id]/links/new`、`…/links/[linkId]/edit` | 病院・会社の名前、職種・配属先、求人票の内容、選考段階、面接官の雰囲気、時間。保存するとリンクができ、コピーできる |
| ④ 結果 | `/agent/seekers/[id]/links/[linkId]` | そのリンクでの練習の一覧(日時・点数)。選ぶと、求職者と同じ結果と、会話の記録の全文 |

- 求職者は削除できる(その求職者のリンクと練習の記録もすべて消す。要件 F-01-6 の考え方)。
- リンクは「使えないようにする」で止められる(止めたリンクを開くと、エージェントに問い合わせるよう案内する)。
- 応募先の内容や面接の設定を直しても、リンクは変わらない(次の練習から新しい内容を使う)。

### 4.2 求職者

| 画面 | URL(案) | 内容 |
|---|---|---|
| ⑤ リンクを開いた最初の画面 | `/i#<リンクの鍵>` | 「〇〇総合病院 二次面接の練習」、名前と時間の目安。音と声の確認(いまの `CheckStep` と同じ:声が届くか、面接官の声が聞こえるか、イヤホン)。「練習の結果は、担当のエージェントにも共有されます。録音はしません」と、全文へのリンク。「面接を始める」 |
| 面接 | 同じ画面の中 | いまの面接ルーム(`RoomStep`)と同じ |
| ⑥ 面接が終わったあと | 同じ画面の中 | いまの結果(`ResultView`)。前回との差。「もう一度練習する」。このリンクでのこれまでの練習(日時・点数。選ぶと結果を見返せる) |

- マイクが使えないときの直し方と、文字で答える面接への切り替えは、いまと同じ。
- 2回目以降にリンクを開いたときも⑤から始める。⑤の下に「これまでの練習」を出す。

## 5. データ

Supabase(Postgres)に保存する。基本設計書 6 章の表をもとに、今回の流れに必要なものだけを作る。

| テーブル | 中身 |
|---|---|
| `user_profiles` | エージェント・管理者(Supabase Auth のユーザーと1対1)。権限(`advisor` / `admin`)、表示名、利用可否 |
| `seekers` | 求職者。担当エージェント、名前、職種、経歴、転職理由。求職者はログインしないため、Auth のユーザーとは結び付けない |
| `practice_links` | 招待リンク。求職者、応募先(名前・職種・求人票)、面接の設定(選考段階・雰囲気・時間)、リンクの鍵のハッシュ、止めた日時 |
| `interview_sessions` | 1回の練習。リンク、開始・終了の日時、そのときの面接の設定と前提情報の写し、会話の記録、状態 |
| `evaluations` | 評価(点数・総評など、いまの `FeedbackResult` の形)。状態(作成中・済み・失敗) |

- リンクの鍵は、推測できない長さの乱数(128ビット以上)にする。データベースには鍵そのものではなくハッシュを置く。
- リンクの鍵は、URL の「#」の後ろに置く(いまの招待リンクと同じ。サーバーのアクセスログや、LINE などのリンクのプレビューに残らない)。画面を開いたら、ブラウザがヘッダーで鍵をサーバーに送る。
- 面接の設定と前提情報(応募先・求人票・経歴)は、**サーバーがリンクから読み込む**。ブラウザから送られた設定は使わない(求職者が書き換えられないように)。
- 会話の記録はいまと同じ形(`TurnRecord` の配列)で、練習1回分をまとめて保存する。基本設計書 6.3 の `turns` テーブル(1発言1行)には分けない。
- アクセス制御:エージェントは自分が担当する求職者・リンク・練習だけ、管理者はすべて(Supabase の RLS でも同じ制限をかける)。求職者の画面からの読み書きは、すべてサーバーがリンクの鍵を確かめてから行う。

## 6. サーバー

- いまの面接の API(`/api/poc/*`)はそのまま使う。入口の確認に「リンクの鍵」を加える:
  - ヘッダー `x-poc-code` が共通の招待コードと一致する(検証ツール `/poc` といまの先行版)、または
  - ヘッダー `x-practice-link` が、止められていないリンクの鍵と一致する。この場合、面接の設定と前提情報はリンクの内容で置き換える。
- 練習の開始と終了を記録する API を加える。終了時は会話の記録を受け取って保存し、評価を作って保存する。求職者が途中で画面を閉じても、評価の作成は最後まで続ける(Next.js の `after()` など)。評価に失敗したら、⑥とエージェントの④から作り直せる。
- 質問計画はいまと同じくサーバーで作ってブラウザが持ち、終了時に会話の記録と一緒に送る。会話の記録はブラウザから送られるが、変えられても影響は本人の結果だけなので、受け取ったものをそのまま保存する。
- 利用回数の上限:求職者1人あたり1日3回・1か月30回(要件 Q-E の推奨)。「面接を始める」を押した時点で1回と数える。上限に達したら、求職者には「今日の練習は上限に達しました。明日また練習できます」と前向きに伝える。
- エージェントの画面のデータは、サーバー側(Server Components・Server Actions)でログインと担当を確かめてから読み書きする。

## 7. ログイン(エージェント)

- Supabase Auth。メールに届くリンクと、同じメールに載せた6桁の確認コードのどちらでもログインできる(LINE の中のブラウザなどで、リンクが別のブラウザで開いてしまう場合に備える)。
- 一般の新規登録は止める。エージェントは、当面は管理者が Supabase の画面(Authentication → Users → Invite)で追加し、`user_profiles` に権限を付ける。
- ログイン状態は Cookie で保ち、`proxy.ts`(Next.js 16 の旧 middleware)で更新する。`/agent` 以下はログインしていなければ `/agent/login` へ移す。
- メールの文面は `supabase/templates/` に置き、本番のプロジェクトにも同じ文面を設定する。

## 8. Supabase がない環境

- 環境変数(Supabase の URL とキー)がないときは、データを**サーバーのメモリに置く代わりの保存先**で動かす(いまの `AI_PROVIDER=mock` と同じ考え方)。ログインも、確認コードを画面に出す代わりの方式にする。本番(`NODE_ENV=production` かつ Vercel の本番)では、この代わりの方式は使えないようにする。
- これで、Supabase のプロジェクトができる前から、手元と e2e で全部の流れを確かめられる。
- データベースの定義(`supabase/migrations/`)と RLS は、テスト用の Postgres(PGlite)で単体テストする。

## 9. 進め方(1機能ずつ。各段階で lint・型チェック・単体テスト・ビルド・e2e を通す)

| 段階 | 内容 | 完了の条件 |
|---|---|---|
| A | データベースの定義と RLS、保存先(Supabase / 代わりの保存先)、エージェントのログイン | PGlite で RLS のテストが通る。代わりの保存先でログインして `/agent` が開ける |
| B | エージェントの画面 ①②③(求職者と応募先の登録、リンクの作成・コピー・停止) | e2e で、求職者と応募先を登録し、リンクをコピーできる |
| C | 求職者の画面 ⑤⑥(リンクから確認 → 面接 → 結果、これまでの練習、利用回数の上限) | e2e で、リンクを開いて面接を終え、結果が出る。もう一度練習できる |
| D | エージェントの画面 ④(練習の一覧、結果、会話の記録)、評価の作り直し | e2e で、求職者が終えた練習の結果をエージェントが見られる |
| E | 要件定義書・基本設計書・README・引き継ぎ書の更新。Supabase の本番のプロジェクトへの接続と実機での確認 | 依頼者が、本物のメールでログインし、スマホでリンクから練習を終えられる |

## 10. 作る人に任せること

- 画面の細かな言葉と並び(見本に合わせ、要件 8.5 の UX-01〜08 に従う)。
- テーブルの列の細部、API のパスの名前、リンクの鍵の文字数(128ビット以上)。
- エージェントの画面をパソコンの幅で広げるかどうか(まずスマホの幅で作り、パソコンでは横に広げる)。

## 11. この設計で作る人が決めたこと(依頼者が確認する)

| No. | 決めたこと | 理由 |
|---|---|---|
| C-1 | エージェントは自分の担当の求職者だけを見られる。管理者はすべて見られる | 個人情報の扱いを必要な範囲にする(要件 8.4)。担当の引き継ぎは管理者が行う |
| C-2 | 求職者の画面に「結果はエージェントにも共有されます。録音はしません」を出し、面接を始めることを同意とする | 要件では「共有するかは本人が選べる」(F-07-11、UX-07)だったが、依頼者の決定 U-4 に合わせて変える。知らせないまま共有しないため |
| C-3 | リンクに期限は付けない。エージェントが止められる | 何回でも練習できる(U-6)ことを優先する |
| C-4 | 利用回数の上限は、求職者1人あたり1日3回・1か月30回 | 要件 Q-E の推奨。費用の歯止め |
| C-5 | いまの先行版(`/join` と共通の招待コード)は残す | 新しい流れが動くまで、いま使っている人を止めない |
| C-6 | 応募先の求人票は、リンクごとに持つ(応募先を複数のリンクで共有しない) | U-6 で、応募先ごとにリンクが1つのため |
