# 段階C：招待リンクからの面接と結果保存

対象：承認済みの招待リンク設計4.2・5・6章。段階Bの管理画面と旧先行版を維持する。

## 実装方針

1. 専用ヘッダーでリンクの鍵を確認。停止・削除済みリンク、違うリンクの練習を拒否する。
2. `/api/practice` で情報・履歴の取得、開始と終了を扱う。開始は求職者単位で日本時間の1日3回・月30回まで。開始の再送には同じIDを使い二重計上を防ぐ。
3. DB版はサーバー専用接続とSQL関数を使う。求職者の行をロックして上限確認と追加を同じ処理で行う。一般のログイン権限には関数を実行させない。メモリ版は上限確認と追加を同じ同期処理内で行う。
4. 開始時点の応募先・経歴・設定を保存。既存の面接APIはリンクを毎回確認し、ブラウザからの応募先や設定を使わない。会話APIは開始済みで未終了の、時間内の練習のみ受け付ける。
5. 終了時は先に会話と計画を保存し、その後に評価を作成する。応答を返してからも `after()` で継続する。終了の再送で会話を上書き・評価を二重生成しない。
6. `/i#<鍵>` は録音を残さないことと担当者への共有を明示。ボタン操作から機器確認を始め、既存の面接ルーム・結果表示を再利用する。マイク不可時は文字入力。結果と履歴はサーバーから取得し、旧先行版の端末保存と混ぜない。

## 検証

- 単体：停止/削除、別リンクの拒否、同時開始、再送、日/月上限と日本時間境界、設定の改ざん拒否、終了の一度だけの保存、応答後の評価。
- DB：既存の定義と新規移行をPGliteで実行。上限、開始/終了の再送、担当者の利用停止、一般権限からの関数実行拒否。
- 通し：未ログインの別ブラウザでリンク→マイク拒否→文字面接→結果→再読込→履歴→再練習→上限→リンク停止。既存5本も再実行。
- lint・型・全単体テスト・buildを確認。実サービス接続と実機音声は別途。

## 次の段階

- 段階D：担当者の結果・全文閲覧、評価失敗の再作成。処理が終了しない評価の回復も含める。
- 段階E：本物の保存先の設定・実機・公開前確認。今回の実装は本番反映や配布の承認ではない。

## 実装時の補足

- URLのフラグメントだけを変えた移動でも読み直す。前のリンクの面接状態は破棄する。
- 開始記録の時刻を既存エンジンへ渡す際、初回の「未開始」判定と衝突しないようにした。回帰テストを追加。
- 機器確認中の応募先変更は、開始時点の写しとの差を見て質問計画も更新する。
- SQL移行はCLIで生成。現在時計の日時が既存の初期移行より前だったため、依存順にファイル名を調整した。実際の保存先には未適用。
